# Event Flow

Event publishing and registration with versioned forms, application review and
admission, staff permissions, Tickets and Attendance, and printable Badges.
Organizers can export CSV data, export/import Event templates, and manage
Communications with frozen history and delivery status visibility.
See [PRODUCT.md](PRODUCT.md) for implemented capabilities and [DOMAIN.md](DOMAIN.md)
for domain invariants.

## Stack

- Next.js 16.3.6 App Router, React 19.3.0, TypeScript.
- Material UI 9.4 with the official Next.js App Router integration and Emotion.
- PostgreSQL 18, Prisma ORM/Client 7.10.0, `@prisma/adapter-pg` and `pg`.
- Better Auth 1.7.6 email/password authentication.
- Zod validation, Temporal for timezone-aware event input, Nodemailer SMTP.
- Biome for linting/formatting; Docker Compose for PostgreSQL and Mailpit only.

## Requirements

Use pnpm 11.23.0 (`packageManager` in package.json), Docker with Compose, and a
Node.js version compatible with Prisma 7.10: `^20.19 || ^22.12 || >=24.0`.
This checkout's commands were verified with Node.js 25.2.1. Application and CLI
tooling run on the host. The production build fetches Google Fonts and needs
network access.

## Local setup

```bash
pnpm install
# For a new checkout only; preserve an existing .env.
cp .env.example .env
```

Before starting services, set `POSTGRES_PASSWORD` for the local database and
populate `BETTER_AUTH_SECRET` with a value generated by `openssl rand -base64 32`.
The auth secret must contain at least 32 characters. Also populate the required
`TICKET_CREDENTIAL_ENCRYPTION_KEY` with 32 random bytes encoded base64url (command
in `.env.example`). Generate it once, preserve it across restarts/deployments and
back it up securely outside the database. Do not reuse the auth secret. Existing
Ticket envelopes cannot be recovered without this key. Keep `.env` untracked.

### Fresh database

For a new, empty database, apply the normal migration history:

```bash
pnpm infra:up
pnpm exec prisma migrate deploy
pnpm db:generate
pnpm db:check
pnpm dev
```

The Node Attendee migration is not needed for an empty fresh database: there are
no historical credentials to rebind.

### Existing populated №20 database → №21A

Follow the canonical [controlled Attendee cutover procedure](docs/attendee-migration.md).
Do not run ordinary `prisma migrate deploy` across prepare and finalize on a
populated №20 database without the intermediate Node data/crypto migration.
Writers, readers and the email dispatcher must remain stopped throughout cutover.

Open the configured `BETTER_AUTH_URL`, initially `http://localhost:3000`, and use
that origin consistently for authentication. Prisma's generated client lives in
ignored `generated/prisma/`; generate it after installing or changing the schema.
Restart a running Next.js server after client regeneration/schema changes.

`prisma.config.ts` loads environment through `@next/env`; `lib/env.ts` validates
settings. `lib/prisma.ts` is the shared server-only client. DATABASE_URL expands
from the POSTGRES variables in `.env.example`; use a URL-safe local password or
percent-encode credentials when constructing a URL.

The migration directory contains an initial development baseline followed by
incremental migrations. The baseline replaces earlier pre-production migration
history; new databases apply the complete migration history. An old disposable local database with the removed
history requires an explicitly authorized reset after verifying its target; this
is not an in-place migration path for a deployed production/staging database.
There is no seed step or demo data.

## Development services

| Service | Default local endpoint | Configuration |
| --- | --- | --- |
| PostgreSQL 18 | `127.0.0.1:5432`, database `event_flow_dev` | POSTGRES_HOST/PORT/DB/USER/PASSWORD and DATABASE_URL |
| Mailpit SMTP | `127.0.0.1:1025` | SMTP_HOST, SMTP_PORT, SMTP_FROM |
| Mailpit inbox | `http://localhost:8025` | Compose binds its HTTP port to `127.0.0.1:8025` |

PostgreSQL uses the named `postgres_data` volume mounted at `/var/lib/postgresql`.
`infra:down` preserves it. Changing initialization credentials in `.env` does not
change credentials inside an already initialized volume. Mailpit captures local
mail instead of delivering it externally; its inbox is ephemeral when its
container is removed. No database or mail service needs a public bind address.

## Authentication development

Register at `/register` with a name, email, and 10–128 character password. Open the
verification link in Mailpit; links expire after one hour. Verification signs the
user in and returns to a safe local `returnTo` destination or `/account`.
Successful sign-in has the same default destination.

An unverified sign-in leads to `/verify-email`; it does not automatically send
another email. Use **Resend verification email** there. Resend has a 60-second UI
cooldown and a server limit of one request per 60 seconds for the endpoint's
rate-limit bucket. SMTP sending is awaited, and failures are reported. Existing
account registration receives a generic response, not another account or an
automatic resend; use the verification screen to request another link.

Sessions last seven days and refresh after one day through Better Auth endpoints;
server session lookups bypass cookie caching. `/account` supports name editing;
email is read-only. Organizer activation is a separate **Become an organizer**
action. Auth or onboarding GET requests do not create OrganizerProfile.

## Historical Ticket backfill

The historical №19 Ticket backfill must have completed before the №21A cutover.
`db:backfill-tickets` is now a retired, explicitly failing tombstone command that
guards against old instructions. Do not use it for fresh setup or №21A migration.
After cutover, a missing historical Ticket is a corruption/investigation case,
never a reason to generate a replacement credential. See the canonical
[Attendee cutover procedure](docs/attendee-migration.md) for existing №20 databases.

Protect both database and encryption-key backups.
Configure any deployment ingress/CDN/access logger to redact `/ticket/*` URLs;
application logging excludes these bearer paths but cannot control upstream logs.
